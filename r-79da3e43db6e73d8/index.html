让 AI 直接读写并部署 Google Apps Script，无需打开浏览器或安装 clasp

需求概括（qiita:228dfa134c76e15ab1a8）：AI 改完 GAS 代码后仍要人打开浏览器手动部署；受限电脑装不了 Node.js/clasp；长代码难定位函数、跨文件同名函数静默覆盖等 GAS 特有 bug 难排查。

为什么值得做：痛点是“受限电脑 + 依赖 AI 写 GAS”这个交集，现有工具几乎全是 MCP 服务器形态、依赖本地 Node.js，恰好绕开了核心场景；竞品检查为 weak，空缺明确。风险有三：一是 Google 侧要走 OAuth 与 Apps Script API，授权审核和配额是硬门槛；二是已有作者自制的『秀GASマネージャー』覆盖了核心流程，虽然只是自用脚本，但说明“够用就好”的用户可能不付费；三是目标人群（用 AI 写 GAS 又被锁电脑）偏窄，付费意愿只有 2。

建议形式：浏览器扩展（在 GAS 编辑器侧边栏注入面板）+ 一个可选的轻量本地桥。

最小可行版本 3 个核心功能： 1. 通过 OAuth 读取当前项目的全部 .gs 文件与函数清单，供 AI 读写； 2. 一键创建新版本并更新部署（不打开 GAS 部署界面）； 3. 跨文件同名函数/未被调用的函数检测与冲突提示。

怎么验证有人要：回复原 qiita 帖并附上可试用链接；在 Qiita 发一篇“不用 Node 也能让 AI 部署 GAS”的实操文；同时发到 r/GoogleAppsScript 和 X 的 GAS 话题下收集前 20 个试用申请。

预计开发天数：10–14 天。

需求概括（hn:50168676）：网站会按 UA 返回不同内容，普通用户无法察觉自己看到的页面与 AI 爬虫或其他设备看到的内容不同（如 WhatsApp 帮助页对 LLM 隐藏了监管机构推荐内容）。

为什么值得做：竞品检查 weak，现有工具都是“UA 切换器”，要用户自己切换、自己肉眼比对，没有工具自动用多个 UA（尤其是 AI 爬虫 UA）抓取同一页面并高亮差异。难度只有 2、单人几天可做完，且话题本身在 HN 上有传播性。风险是需求可能一次性——用户查过一次就不再打开；另外跨域抓取受 CORS 限制，需要用后台 fetch 或代理，部分站点会直接 403。

建议形式：Chrome 扩展。

最小可行版本 3 个核心功能： 1. 对当前标签页 URL，用普通浏览器 / GPTBot / ClaudeBot / Googlebot 等若干 UA 分别抓取； 2. 归一化后做正文差异高亮，标出“只对某一方可见”的段落； 3. 保存最近检测记录，并在命中差异时给出角标提示。

怎么验证有人要：回复原 HN 帖；发 Show HN；在 r/webdev、r/privacy 各发一次，观察是否有人主动报“帮我查查某站”。

预计开发天数：4–6 天。

需求概括（qiita:7891fed6c9eaae905bc6）：想按早晚批量阅读关注领域的文章，不想被逐条通知打扰，也不想同一篇文章被重复追加。

为什么值得做：竞品检查 weak——搜索结果全是教程代码或需自行部署的 GitHub 脚本，没有开箱即用、带配置界面（添加 RSS、设定早晚时间、自动去重）的网页工具；作者自己的脚本也需手动建表、填表头、配触发器。风险是这类需求“教程已经够用”，付费意愿只有 2，且 Feedly、Zapier、IFTTT 覆盖了相邻场景；真正愿付钱的是不想碰 GAS 编辑器的非技术用户，规模有限。

建议形式：网页工具（OAuth 授权后自动建表、写触发器，用户不接触代码）。

最小可行版本 3 个核心功能： 1. 粘贴多个 RSS/Atom 源，设定每天早晚两个抓取时间； 2. 按标题 + 链接 + 发布时间去重后追加到指定 Google 表格； 3. 抓取失败/配额超限的可视化状态与重试。

怎么验证有人要：回复原帖；在 Qiita 写一篇“不写一行 GAS 也能做早晚新闻表”；把工具发到 r/rss 和 X 的 GAS 社群，统计授权建表人数。

预计开发天数：5–7 天。

需求概括（qiita:723f8fccd84e39f9c666）：微软日语 IME 汉字转换后必须按 Tab 才打开候选列表再按数字选词，大量输入日语时极其烦人；又不想为此安装第三方输入法。

为什么值得做：痛点高频且情绪强，竞品检查 weak，现有方案都是个人写的 AutoHotkey 脚本（作者自己的 NoTabKana，MIT），没有安装包、配置界面、开机自启和更新分发——这正是“从脚本到产品”的空缺。风险：一是 NoTabKana 已开源，用户可以直接拿去用，付费理由弱（付费意愿 2）；二是 Windows IME 与安全软件对键盘钩子敏感，容易误报，不同版本 IME 行为差异需要长期维护。

建议形式：Windows 桌面应用（安装包 + 托盘设置）。

最小可行版本 3 个核心功能： 1. 数字键自动补 Tab 并直接选词、=/- 翻页； 2. 托盘开关、开机自启、按进程白名单启停； 3. 一键安装包与版本更新提示（不要求用户装 AutoHotkey）。

怎么验证有人要：回复原帖并附安装包；在 Qiita 发使用前后对比文；发到 X 的日语输入话题和窓の杜类投稿渠道，统计下载与“按键不生效”的反馈比例。

预计开发天数：6–9 天。

跨平台共同需求

同一需求被多平台重复提出的情况很少（只有 qiita:228dfa134c76e15ab1a8 和 qiita:723f8fccd84e39f9c666 各出现 2 次，且都在 qiita）。更明显的是几种跨平台的“诉求模式”：

  1. “个人脚本已经能跑，但没人把它做成产品”。qiita 上大量条目标注“部分解决：作者自己已做出……但只是个人脚本”，如 qiita:7891fed6c9eaae905bc6、qiita:4e417be09c6cf64547b3、qiita:8f9489403e10f585c3af；HN/SE 上则是“回复里给了个 GitHub 脚本”的形态，如 se:softwarerecs:95686。差别在于：日文侧倾向于把自用脚本当原型，直接讨论产品化；英文侧更常停在“有开源实现就够了”。

  2. 本地化或受限环境下的 AI。qiita:228dfa134c76e15ab1a8（受限电脑装不了 Node.js/clasp）、gh:microsoft/vscode#338860（禁止 Copilot 回退到外部模型）、qiita:a98b283eed4045391dc0（离线日语 LLM）、hn:49627397（桌面端侧模型）指向同一件事：数据不出门、依赖不落地。日文侧强调“出差/客户现场”，英文侧强调“合规与费用”。

  3. 在编辑器内让 AI 产出的引用可点击、可追溯。gh:microsoft/vscode#341290（issue 编号转链接）、#336248（PR 悬停富预览）、#342543（链接悬停预览）、qiita:81cf8f1140fe58f36e66（把浏览器里的指令传进 Codex 会话）本质相同；GitHub 侧希望官方改渲染层，qiita 侧则自己搭 MCP + 扩展绕过。

  4. 浏览器里“实时判断并标记”。hn:50168676（UA 差异）、hn:50144294（私募股权标记）、hn:49656324（条款风险）、hn:49582536（AI 生成文字渐隐）、qiita:25b8a7b52819035bba5b——都是“不用手动比对，浏览时就给我结论”。英文侧偏隐私与信息不对称，日文侧偏阅读效率。

  5. 输入、焦点、窗口的失控感。qiita:723f8fccd84e39f9c666（IME 要按 Tab）、hn:50107094（启动器抢焦点）、hn:50017797（快捷键符号记不住）、gh:microsoft/PowerToys#50482（三指拖拽）——Windows 侧抱怨“缺 macOS 的体验”，macOS 侧抱怨“缺图形化开关”。

不建议做的

  1. VS Code 原生 UI 细节类 issue：如 gh:microsoft/vscode#343293（滚动条遮挡选项）、#345151（隐藏 AI 更新日志）、#343902、#344616、#340650、#338183、#335423、#339486、#343904。这些都在官方 backlog 里，插件只能靠修改 CSS 或非公开 API 实现，官方一实现就归零；付费意愿普遍是 1–2。

  2. 依赖第三方产品内部 Feature Flag 的改造：如 qiita:207104b10a46ea6d9960（恢复 Claude 的 Chat/Cowork 分离界面）。作者自己都写明“易随官方更新失效”，一个人无法承担持续逆向的成本。

  3. 重资产或强专业领域：qiita:d696ddf067eddde79e7f（短视频全自动流水线，作者自己都撞上浏览器内存上限）、qiita:a5e7ce5c9a32f976e339（RTSP 验收）、qiita:77c6bc5c47d0264d1aff（UDS/DoIP）、se:softwarerecs:95686（流量生成回归测试）、qiita:1511f46212883dcacca2（Exchange Online 批量配置）。需要领域知识、企业级可靠性和销售，不是一个人用 AI 几天能交付的。

  4. 已有成熟免费方案或官方已覆盖：hn:49806516（macOS 关鼠标加速，LinearMouse 等已覆盖）、hn:49886395（Knockoff、Fakespot）、qiita:5e6a7ae69019b75374b1（commitlint/husky/commitizen 已够用，只是配置麻烦）、qiita:50e587e6c541e0089769（ChatGPT 官方 Library 已支持 Dropbox 目录浏览）、hn:49861720（better YouTube preview 已实现长按预览）、gh:microsoft/PowerToys#50482（ThreeFingerDragOnWindows 已有 1.1k stars）。

  5. 付费意愿极低的一次性微工具：se:softwarerecs:95654（按页数筛 PDF，需自建索引，难度与回报不匹配）、hn:49602056（HN 更丰富评价机制，平台不改就没用）、qiita:70e09095d14bb87757ab（日文字数统计，浏览器已有多种替代）、gh:microsoft/vscode#343293 这类“只影响一次操作”的体验修补。做出来也很难收回开发时间。

英文、日文、中文社区的差异

日文（qiita）：这个数据集里占比最大，特征是“自建脚本先行”。大量条目的“现有方案”写的是“作者自己已经用 GAS / Python / AutoHotkey / MCP 做出来了，但只是个人脚本”，需求本质是产品化与分发（安装包、配置界面、多用户、更新），而不是从零发明。领域上办公自动化特别密集：Google 表格、收据 PDF、Excel 宏库、Notion 表单、报销审计、Kakuyomu 数据、ブクログ藏书。本地化细节（和历日期、敬称、发票登记号、日本地址全角半角、日语 IME）构成天然护城河，但单点市场小、付费意愿普遍标 2–3。另一个明显集群是 AI 编码代理周边（Claude Code、Codex、MCP、GAS 部署），作者多是重度个人开发者。

英文（Hacker News / StackExchange / GitHub issues）：更多是平台级缺口与协议层问题——Web Push 自托管（se:softwarerecs:95677）、UA 差异（hn:50168676）、API 破坏性变更追踪（se:softwarerecs:95656）、C2PA 截图来源（gh:flameshot-org/flameshot#4978）、passkey 统一关闭（hn:49755505）。GitHub issue 型需求则是开源项目内的原生功能诉求，特点是“官方总有一天会做”，做插件窗口期短。英文侧隐私、合规、安全的诉求更集中，且偶尔出现付费意愿明显偏高的垂直场景（VST 吉他插件、Withings 健康同步、系统级音频）。

中文：本次数据中没有中文社区的条目，无法比较。若要把上面结论外推，需要另行收集中文社区样本再判断——尤其“个人脚本产品化”和“办公表格自动化”这两类在中文语境下是否同样成立，目前没有数据支持。

机会判断：日文侧适合做窄而深、带日语界面和本地规则的付费小工具，靠 Qiita 文章 + 原帖回复冷启动；英文侧适合做开发者自己会用的浏览器扩展或 CLI，靠 Show HN、Chrome Web Store、VS Code Marketplace 分发，但同质化和免费竞品更多，必须在“自动化比对/自动判断”这一点上做出差异，否则很快被现成脚本淹没。
