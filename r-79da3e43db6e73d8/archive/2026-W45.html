检测网站按 User-Agent 返回不同内容的浏览器扩展（hn:50168676）

展开详情
  • 需求概括：网站会根据 UA 给普通用户、AI 爬虫、不同设备返回不同内容，用户无法察觉。现有工具要么只切换 UA、要么只看单一爬虫视角，没有并排高亮差异的方案（竞品检查：weak，空缺明确）。
  • 为什么值得做：难度 2、付费意愿 2，Chrome 扩展形态最适合一人开发；痛点是“看不见的差异”，演示效果强，容易在 HN/隐私社区传播；不依赖任何平台内部 API。
  • 建议形式：Chrome 扩展，弹窗内并排对比。
  • 最小可行版本的 3 个核心功能： 1. 输入当前 URL，自动用“普通浏览器 UA”和“指定 LLM 爬虫 UA”各取一次页面。 2. 对正文做块级 diff，高亮只在一侧出现的文本。 3. 保存对比快照，支持复制差异摘要。
  • 怎么验证有人要：回复原帖附原型截图；发 Show HN；在 Reddit 的隐私/前端相关板块发测试邀请；找做 AI 内容审核或 SEO 的人试用。
  • 预计开发天数：5–7 天。

英文社区与日文社区的差异
  • 需求层次不同：英文侧（hn、se、github）更多落在平台、协议和基础设施层，例如 se:softwarerecs:95677（自托管 Web Push）、se:softwarerecs:95656（依赖破坏性变更追踪）、se:softwarerecs:95688（Android 焦点窗口 JSON）、gh:microsoft/vscode#337592（BYOK OAuth 令牌）。日文侧（qiita）更多落在个人工作流和业务文档，例如 qiita:228dfa134c76e15ab1a8（GAS 部署）、qiita:df2fb24f6a0bfec5bb13（VBA 宏库）、qiita:67fece9a9434bfd9fed8（验收清单）、qiita:4e417be09c6cf64547b3（收据 PDF）。
  • 浏览器扩展的动机不同：英文侧偏向“过滤、屏蔽、对比、防骗”，如 hn:49904611、hn:49886395、hn:50144294、hn:50168676、hn:50022196。日文侧偏向“白名单、合规、防误触”，如 qiita:497627e449caa8b4e465、qiita:3c2c7675661590a4309a。
  • 对“部分解决”的态度不同：日文作者普遍已经用 GAS、Python、AutoHotkey、Claude Code 做出原型，缺的是安装包、UI、多用户和免配置；英文侧更多是 issue 提案，等官方或第三方补缺口。前者适合做“产品化封装”，后者适合做“独立替代工具”。
  • 本地化壁垒不同：日文侧有和历、敬称、发票登记号、日本地址、SUZURI、Kakuyomu、ブクログ、居酒屋排序等细节，海外工具难以覆盖；英文侧需求更通用，竞争也更直接。
  • 付费意愿分布不同：日文侧付费意愿 3 集中在“对客户交付、合规、省人工”的场景，如收据、表单→Notion、验收清单、客服检索、Exchange 日历；英文侧付费意愿 3 多在开发者基础设施、健康和隐私安全场景。
  • 各自的机会：英文侧适合做通用、隐私优先、可自托管的小工具，靠 Show HN、Reddit 和垂直社区获客；日文侧适合做“日本本地化 + 开箱即用”的网页工具或插件，靠 Qiita 实操文章和 X 传播，面向小团队和自由职业者按次/按月收费。
