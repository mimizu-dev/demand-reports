跨平台共同需求

1）钓鱼/恶意站点防护：一个要“判断”，一个要“默认拒绝” - hn:49972370：现有 Google Safe Browsing 等是黑名单式，对新型社工与定制钓鱼覆盖不足，缺的是对邮件内容上下文的二次判断。 - qiita:497627e449caa8b4e465：同一痛点换了个解法方向——做白名单浏览器，只允许已授权域名，顺带解决广告关闭按钮误触。 英文侧要“告诉我这条可不可信、为什么”，日文侧要“干脆不让我打开”。两者的共同结论都是现有黑名单/警告不够用。

2）AI 调用的成本、额度与状态不可见 - gh:microsoft/vscode#337964：要在 VS Code 原生徽章里看到第三方网关的 token 与花费（帖子出现在 github/hn/qiita 三处）。 - qiita:85a0381a26dc85468ff0：把多订阅聚合成一个 OpenAI 兼容端点，额度用尽自动切换。 - qiita:b3df525ee38941ec98f8：429 后强制冷却，防止代理自行绕过规则。 - qiita:5aa037294434003db2db：Codex 进入等待批准/输入时通知人。 同一个黑盒问题，IDE 侧表述为“UI 里看不到成本”，CLI 侧表述为“额度会突然断、任务会卡住没人知道”。

3）把事件推送到手机 / Discord - qiita 侧一律用 Discord Webhook 拼装：qiita:5aa037294434003db2db、qiita:d7131f574eb87d7f412c、qiita:aa04078ea2e698e64ea9。 - se 侧明确排斥绑定某个聊天客户端：se:softwarerecs:95677 要自托管、多用户、CLI/curl 触发的原生 Web Push。 共同点是“离开电脑后要知道发生了什么”，差别是日文社区接受“用 Discord 就行、只要免配置”，英文社区要“不依赖第三方聊天服务”。

4）操作系统缺一个理所当然的小开关 - 日文侧偏输入与常驻指示：qiita:3619d135ea81edf13f58（微软日语 IME 数字键直选候选）、qiita:bff84f6e3a3cbedb7827（VS Code 终端里日文 IME 乱码）、qiita:f236175ab4e6cc85943b（锁定键状态常驻角落）。 - 英文侧偏窗口与指针行为：hn:50107094（阻止 Epic/Steam 抢焦点）、hn:49806516（macOS 关鼠标加速）、hn:50017797（把 ⌘⌥⇧ 显示成文字）。 都是“系统级一行设置的事，但官方就是不做”。

5）不信任 AI 输出的稳定性 - 日文侧要格式与措辞可控：qiita:f1980afd016722bd6b44（固定章节+类型校验+回退）、qiita:25b8a7b52819035bba5b（结论先行、压缩篇幅）、qiita:67fece9a9434bfd9fed8（改写成业务方看得懂的验收步骤）。 - 英文侧要可复现对比：hn:50060564（标准化记录 prompt/输出/token，公平比较模型能力）。 一个想做“约束输出”，一个想做“审计输出”。

最值得做的 5 个

1

邮件/链接可信度的上下文二次判断扩展

需求概括：hn:49972370（最终分 8.1，全场最高；帖子数 3；热度 1.80，一周前 2.12，正在降温）。普通用户识别不了新型钓鱼邮件和恶意链接，企业级安全工具又用不上。

为什么值得做：帖子数 3 且跨帖重复出现，说明是长期共性痛点；现有方案明确只做黑名单匹配，对定制化社工和“上下文不对劲”的判断是空白。付费意愿只有 2，所以不要指望订阅制，应该走“免费扩展 + 隐私口碑 + 后续专业版/团队版”。热度在降，说明不是爆发窗口，要尽快用最小成本验证。

建议形式：Chrome 扩展（MV3）。卖点是“邮件正文不出本机”——本地启发式 + 可选本地小模型，或让用户自填 API Key。

MVP 三个核心功能： 1. 选中邮件正文或链接后一键分析：提取发件人域名、显示文字与实际 URL 的差异、紧迫性话术、域名是否首次见到。 2. 输出三档结论（安全/可疑/高风险）+ 三条以内可读理由，而不是一个概率数字。 3. 本地记录“首次见到的域名”并允许用户自建白/黑名单。

怎么验证：直接在 hn:49972370 原帖回复，说明你打算做什么并征集 20 个真实钓鱼样本做公开对比页；发 Hacker News 的 Show HN 与 r/phishing、r/cybersecurity；用你自己收到的钓鱼邮件做录屏 demo。

预计开发天数：10~14 天。

2

检测网站对不同 User-Agent 返回不同内容的扩展

需求概括：hn:50168676。WhatsApp 帮助页面对 LLM 隐藏了推荐监管机构的内容，普通用户看不到自己和 AI 爬虫看到的页面不一样。

为什么值得做：竞品检查为 weak 且空缺写得很具体——现有工具要么只切换 UA 不对比、要么只呈现单一爬虫视角、要么只做 Googlebot/SEO。难度 2，纯前端双请求 + diff，一个人两三天就能出原型。目前只有 1 帖，属于“概念容易传播、但需要你替它制造话题”的类型。

建议形式：Chrome 扩展（侧栏并排双视图 + 差异高亮）。

MVP 三个核心功能： 1. 对当前 URL 分别以普通 UA 与 LLM 爬虫 UA 各请求一次，并排渲染。 2. 文本 diff：高亮“只给爬虫看的”和“只给人看的”段落。 3. 一键生成对比截图/摘要，便于发帖曝光。

怎么验证：回复 hn:50168676 原帖请发帖人试用；发 Show HN 与 r/webdev；先自己扫 200 个常用站点做一份“哪些站点对 AI 隐藏内容”的公开榜单来引流。

预计开发天数：5~8 天。

3

Gmail 里识别“群发式个性化”招聘邮件的扩展

需求概括：hn:50022196。招聘方用自动化工具批量发送看似个性化的邮件，收件人只能逐封人工分辨。

为什么值得做：竞品检查 weak 且空缺明确（现有只有通用垃圾/关键词分类，或只覆盖 LinkedIn/特定招聘平台的老脚本）；付费意愿 3，是这个列表里少见的“消费者愿意掏钱”的场景；难度 3，扩展 + 少量判定逻辑即可。热度 0.57（一周前 0.68）在降温，但求职是周期性刚需。

建议形式：Chrome 扩展（Gmail 内容脚本）+ 轻量后端或本地规则，不需要自建大系统。

MVP 三个核心功能： 1. 判定“是否招聘邮件”（发件域名、模板化措辞、追踪链接）。 2. 打标签“疑似群发 / 疑似真人”：依据是否含本人姓名与简历具体经历、是否带 List-Unsubscribe 等批量头发件域。 3. 在 Gmail 侧栏一键折叠/归档所有群发，只留真人邮件。

怎么验证：回复 hn:50022196 原帖；发 r/jobs、r/recruitinghell（痛点人群最密集）；用 50 封真实招聘邮件做一份判定准确率报告公开。

预计开发天数：8~12 天。

4

需求定义书 → 用户视角验收清单（带截图栏与需求 ID 覆盖）

需求概括：qiita:67fece9a9434bfd9fed8。开发者写的验收清单全是术语，业务方看不懂该点哪里；还缺截图栏和需求 ID 覆盖检查。

为什么值得做：竞品检查 weak，空缺是三合一能力（术语改写成用户操作、内置截图栏、按需求 ID 覆盖校验），不是单点功能；付费意愿 3，面向受託開発/QA 小团队，能收钱。虽然标了“部分解决”，但作者只是提示词模板 + 一个覆盖检查的 Python 小脚本，没有产品——空缺明确，可以做。难度 3，网页工具即可。

建议形式：网页工具（上传文档 → 生成表格 → 截图归档 → 导出）。

MVP 三个核心功能： 1. 上传 md/docx/txt 需求定义书，按需求 ID 生成“用户视角操作步骤”（点哪里、应看到什么）。 2. 每条检查项内置截图栏，支持拖拽/粘贴截图。 3. 需求 ID 覆盖率校验（列出未被任何检查项覆盖的需求）+ 导出 Excel/PDF。

怎么验证：回复 qiita 原帖（作者本人就是这个用户，最容易拿到第一批反馈）；在 Qiita 写一篇后续文章挂工具链接；找 2~3 个日本小型受託開発团队免费试用换证言。

预计开发天数：12~15 天。

5

让 Obsidian Callout 内容跟随当前视图模式

需求概括：forum:obsidian:120058。Callout 内部始终按阅读视图渲染，导致 %%注释%% 不显示、连续空行被折叠，编辑时看不到真实内容。

为什么值得做：竞品检查 weak 且写得很明确——没有插件直接解决这一核心需求，社区只有零散 CSS 片段，改不了渲染模式；官方无方案。难度 3，是一人可做的插件级工作量，且 Obsidian 社区插件市场分发成本几乎为零。付费意愿 2，指望不上订阅，但可以做成引流/赞助型开源插件。注意原帖里有观点认为插件难以覆盖默认行为，所以第一步是技术可行性验证，别直接投入两周。

建议形式：Obsidian 社区插件（CodeMirror 6 扩展 + 后处理）。

MVP 三个核心功能： 1. 检测当前是 Live Preview 还是阅读视图。 2. 让 Callout 内的注释与连续空行按当前模式显示（Live Preview 下显示注释）。 3. 一个设置开关 + 仅当前文件/全局生效的选项。

怎么验证：在原帖 forum:obsidian:120058 回复贴出 10 秒 GIF 原型（这是最直接的判定）；发 Obsidian 官方论坛插件区、r/ObsidianMD、Obsidian Discord 的 #plugins 频道。

预计开发天数：7~10 天（含 CM6 调试，若技术验证失败则止损在前 2 天）。
