需求概括（qiita:228dfa134c76e15ab1a8）：AI 改完 GAS 代码后仍需人手动打开浏览器部署新版本；受限电脑装不了 Node.js/clasp；GAS 的长代码难定位函数、跨文件同名函数会静默覆盖。帖子数 2，热度从 0 升到 2.03，是本批唯一最终分 5.7 的需求。

为什么值得做：竞品检查为 weak，且空缺非常具体——现有工具几乎都是 MCP 服务器形态、依赖本地 Node.js 运行，恰好绕不开"受限电脑装不了 Node.js"这个核心痛点；也没有工具专门做 GAS 的跨文件同名函数冲突检查。这是一个"别人做了一半、方向偏了"的位置，不需要教育市场。 风险要写明：①作者自己已有『秀GASマネージャー』覆盖核心逻辑（部分解决），差异化只能落在"免 Node.js 的安装分发 + 多用户配置界面"，做不出这层就只是复刻；②需要 Google OAuth 授权与 Apps Script API 的部署权限，凭证托管、刷新令牌、企业管理员策略拦截都是真实的落地阻力；③"软件插件"形态和"不打开浏览器"本身有张力，必须想清楚是本地服务 + 本地网页，还是纯扩展。

建议形式：单二进制本地服务（Go/Rust 或 Tauri 打包，不依赖 Node.js）+ 浏览器打开 localhost 配置页。一个人 AI 辅助开发可控，也正好对上"受限电脑"。

最小可行版本 3 个核心功能： 1. OAuth 授权后列出账号下所有 GAS 项目与已有部署，选择目标项目/部署 ID。 2. 把本地目录或粘贴的代码按文件写入项目，并直接创建一个新版本、更新指定部署（全程不打开浏览器编辑器）。 3. 写入前的静态检查：跨文件同名函数、重复函数声明、部署前后 diff，输出一份冲突报告。

怎么验证有人要：回到原 Qiita 文章评论区贴可运行 demo；发到 Qiita/Zenn 的「Google Apps Script」标签、r/GoogleAppsScript、HN 的 Show HN；先做一个"不装 Node 也能部署 GAS"的单页录像 + 等待列表，看有多少人愿意留 GAS 项目数和使用场景。

预计开发天数：14–18 天（OAuth + Apps Script API 部署链路占一半）。

需求概括（hn:50168676）：网站会根据访问者 UA 返回不同内容，普通用户无法察觉自己看到的页面与 AI 爬虫或其它设备看到的有何差异（例如 WhatsApp 帮助页面对 LLM 隐藏了推荐监管机构的内容）。难度 2，竞品 weak。

为什么值得做：空缺干净——现有工具全是"UA 切换器"，面向开发者，要用户自己切换、自己肉眼比对，没有工具自动用多个 UA（尤其是 AI 爬虫 UA）抓同一页面并做差异高亮。概念新、demo 性极强，一条对比截图就能传播，是这批里最适合一个人 5 天出一版、靠内容获客的选题。 风险：①只有 1 个帖子，热度 0.73 且一周前 0.86，属降温，需求强度未经多人验证；②纯前端扩展抓取受 CORS 与登录态限制，很多页面换成爬虫 UA 后直接返回 403，需要明确的失败降级；③A/B 测试、地区差异、登录态都会造成误报，差异算法的准确度决定口碑；④受众是记者、研究者、SEO、开发者，付费意愿 2，短期只能靠开源 + 赞助。

建议形式：Chrome 扩展 + side panel 并排 diff，抓取放在 background service worker，可选的自建中转代理作为进阶开关。

最小可行版本 3 个核心功能： 1. 一键用一组 UA（Chrome / Safari / GPTBot / ClaudeBot / Googlebot）抓取当前 URL，并排展示正文。 2. 自动高亮"仅在某 UA 下出现或消失"的段落，并给出差异摘要。 3. 结果导出为 Markdown + 对比截图，方便直接贴到帖子里。

怎么验证有人要：直接在 HN 原帖回复一个可用版本（这条帖子本身就有讨论热度）；发 Show HN、r/webdev、r/TechSEO；拿 WhatsApp 帮助页这类已知案例录 60 秒对比视频。

预计开发天数：5–7 天。

需求概括（qiita:7891fed6c9eaae905bc6）：想按早晚批量阅读关注领域的文章，不想被逐条通知打扰，也不想同一篇被重复追加。现有方案要么是 Feedly 这类不易导出到表格的阅读器，要么是按任务计费的 Zapier，作者自己写了 GAS 脚本但需手动建表、填表头、配触发器。

为什么值得做：竞品 weak，搜索结果里全是教程代码和需自行部署的 GitHub 脚本，没有带配置界面（添加 RSS、设早晚时间、自动去重）的开箱工具；作者自己的脚本属部分解决，空缺正是"开箱即用 + 配额与失败处理"。GAS 生态的日语用户基数大，做成向导型网页工具边际成本低。 风险：①和 Feedly/Inoreader 正面重叠，用户很容易觉得"用阅读器就行"，必须把卖点锁在"进我的表格、我能二次筛选"而不是"读 RSS"；②GAS 有 6 分钟执行上限和 UrlFetch 配额，源一多就要分批与断点续传，这部分不做完会大量失败；③付费意愿 2，只能做免费引流或一次性小额。

建议形式：单页 Web 配置向导 + 一键生成并部署到用户自己账号的 GAS（用户保留数据所有权），而不是自己托管抓取服务。

最小可行版本 3 个核心功能： 1. 粘贴 RSS 列表或导入 OPML，按关键词/分组管理，设定早/晚两个推送时间。 2. 按 URL 归一化 + 标题相似度去重后写入表格，带来源、首次收录时间、分组列。 3. 一键生成带触发器的 GAS 代码并引导授权；内置运行日志与配额/失败告警页。

怎么验证有人要：回复原帖并附上"3 分钟从零到第一行数据"的录屏；发 Qiita 的「Google Apps Script」「RSS」标签、X 上的 GAS 社区；用同一份 OPML 做一次"手工配置 vs 向导配置"的耗时对比。

预计开发天数：6–9 天。

需求概括（qiita:b5fb1ca9e460c7e14b9e）：Wan 2.5 要求把画面描述、台词、环境音和 BGM 写进同一段提示词，手写时顺序容易乱、台词容易被误改，导致效果不稳定、难以对比多个镜头。作者自己写了个 Python 函数按固定顺序拼接，但没有界面、不支持多镜头管理、模板保存和导出。

为什么值得做：难度 2，是名单里最轻的一档，一个人 3–4 天能出成品；竞品 weak，现有只有一个 Qiita 上的 Python 函数，缺的正是"网页表单 + 多镜头 + 模板"，空缺边界清楚，不需要猜。作者已经用自身使用验证了"顺序固定能提升稳定性"，需求真实性有背书。 风险：①深度绑定单一模型，Wan 一旦修改提示词规范或换版本，工具价值立刻缩水，必须设计成可切换的模板/字段配置；②视频生成玩家对"表单工具"付费意愿 2，几乎只能靠免费 + 引流；③通用提示词助手很多，容易被认为"我用 Notion 模板就行"。

建议形式：单文件静态网页，纯前端 + localStorage，可离线双击打开、可直接部署到任意静态托管。

最小可行版本 3 个核心功能： 1. 画面 / 台词 / 环境音 / BGM 分字段输入，按固定顺序实时拼出最终提示词，一键复制。 2. 多镜头列表：新增、重命名、排序、整组导出/导入 JSON。 3. 模板库与校验：常用镜头片段复用，台词字段在拼接后原样回显并给出"是否被改写"的对照。

怎么验证有人要：回复原帖并附上同一组镜头"手写 vs 工具"的生成结果对比；发 Qiita 与 X 的 Wan / 视频生成话题、Reddit 的 AI 视频板块；把 3 组前后对比样片做成一条短贴。

预计开发天数：3–4 天。

需求概括（qiita:723f8fccd84e39f9c666）：Windows 微软日语 IME 汉字转换后必须按 Tab 打开候选列表再用数字选词，大量输入日语时反复敲 Tab 很烦，又不想为此装 Google 日语输入或 ATOK。作者已用 AutoHotkey v2 写了 NoTabKana（MIT 开源），但只是个人 AHK 脚本，缺安装包、配置界面、开机自启、对其他 IME 的兼容与更新分发。帖子数 2。

为什么值得做：竞品 weak，现有方案全是个人 AHK 脚本，要求用户自己装 AutoHotkey、自己改脚本，没有打包成桌面应用、没有维护与兼容性保障——这正是可产品化的空缺。受众明确且高频（每天打字都能感知收益），口碑传播路径清晰（日语输入相关社区）。 风险：①需要全局键盘钩子，容易和游戏、远程桌面、其他 IME、安全软件冲突，杀软误报是常态；②Windows 更新可能破坏 hook 行为，长期维护成本高于开发成本；③付费意愿 2，多为一次性小工具，商业上限低，更适合开源 + 捐赠或做成合集的一部分。

建议形式：Windows 原生托盘应用（C#/Rust 单 exe，无外部依赖），保留 AHK 版作为轻量替代；配置项走托盘菜单而非复杂 GUI。

最小可行版本 3 个核心功能： 1. 全局钩子实现"数字键直接选候选（等价 Tab+数字）"与 =/- 翻页键映射。 2. 托盘开关 + 按应用白/黑名单（排除游戏与远程桌面）。 3. 开机自启、一键安装/卸载，并支持导入现有 NoTabKana 配置。

怎么验证有人要：回复原帖并接手其 GitHub issue，公开"打包版 vs 原 AHK 脚本"的安装步骤对比；发 Qiita 的日语输入话题、X 的 Windows/IME 用户群、日本软件介绍类投稿；先开源免费收集兼容性反馈，再考虑付费打包。

预计开发天数：7–10 天。

英文、日文、中文社区的差异

先说数据边界：本次数据集里没有中文社区样本（平台只有 qiita、hn、se:softwarerecs、forum:obsidian、github），因此中文一侧无法比较，下面只对比英文（HN / SoftwareRecs / GitHub / Obsidian 论坛）与日文（Qiita）。

英文社区：先骂产品，再想办法 - 需求起点多为"某个产品做错了什么"：UA 差异（hn:50168676）、AI 生成文字（hn:49582536）、私募股权收购（hn:50144294）、推荐算法塞广告（hn:49793876）、passkey 强制弹窗（hn:49755505）、工作软件窥探个人账户（hn:49677927）。用户已经在描述一个结构性不信任，工具只是手段。 - GitHub 一侧则是另一个极端：极其细碎的单点行为（窗口宽度、滚动条遮挡、悬停卡片、折叠层级），付费意愿普遍 1–2，本质是"给上游提 issue"，不适合当产品做。 - 付费意愿的分布很两极：绝大多数 1–2，但出现少量 3–4 的明确场景（hn:50085840 虚拟吉他 VST 付费意愿 4、qiita:725bc1f282b666db065a 报销审计 4、qiita:d291961b9141a51f173b Slack 任务 4）。 - 机会点：横向工具 + 一次安装覆盖多站点（浏览器扩展、系统级小工具），但要先算清楚"官方或免费替代有多近"。
