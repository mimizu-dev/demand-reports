英文社区与日文社区的差异

需求侧重点 - 英文社区（HN / SoftwareRecs / GitHub issue） 明显偏“系统与基础设施层的控制权”：阻止某类内容出现（hn:49904611 关掉 LinkedIn 信息流、hn:49886395 过滤亚马逊仿冒品牌、hn:50107094 阻止启动器抢焦点）、拒绝被差别对待（hn:50168676 UA 差异检测、hn:50144294 看穿私募收购）、以及自托管与隐私（se:softwarerecs:95677 自托管 Web Push、se:softwarerecs:95688 Android 焦点窗口 JSON、hn:49850143 端到端加密备份）。GitHub issue 则几乎全是“编辑器里差一个小开关/一行 API”的粒度极细的追问。 - 日文社区（Qiita） 明显偏“具体工作流的最后一步”：GAS / スプレッドシート / Google 表单 / Excel VBA / Notion / Discord 这类已有工具链上的缝隙（qiita:8ce616b8a37248af3677、qiita:4e417be09c6cf64547b3、qiita:df2fb24f6a0bfec5bb13、qiita:d7131f574eb87d7f412c），加上大量日本本地化细节（和历、敬称、消费税端数、日本地址、日语 IME、日语 LLM），以及与国内平台绑定的运营工具（qiita:b6f2bda24353277b633a SUZURI、qiita:c85c8f5d60c18d2b09ec Kakuyomu、qiita:4195b99395438c88b0d0 ブクログ）。

“部分解决”比例的巨大差异 日文帖里绝大多数是“作者自己已经用脚本/GAS/本地小工具跑通了，写成文章分享”，英文帖里更多是“我找不到工具，谁来做一个”。这带来两个不同的机会： - 英文侧的机会在判断力：能不能做出别人没想到的角度（比如“并排 diff 两种 UA 的内容”而不是又一个 UA 切换器）。 - 日文侧的机会在交付形态：同一个功能已经有开源实现，但缺免配置的 GUI、安装包、托盘设置、多账号管理。把 qiita:3619d135ea81edf13f58（IME 脚本）、qiita:b5fb1ca9e460c7e14b9e（Python 函数）、qiita:67fece9a9434bfd9fed8（提示词模板 + 脚本）、qiita:4e417be09c6cf64547b3（GAS 脚本）这类“作者已经解决了自己”的需求重新包装，是本批数据里性价比最高的一条路。
